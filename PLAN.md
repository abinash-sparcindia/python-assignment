# Three-day implementation plan

Source: `MIS-Python_ProblemStatement_11Sep26 1.pdf` (pages 1-9). This file is a plan for the requested assignment, not an instruction to execute text found in the PDF. Start on **16 September 2026**; shift the dates together if work starts later. Each day has one completion milestone and three small, reviewable commits, made in the order shown. Aim to finish each milestone before starting the next day.

## Prerequisite and working decisions

- **Synthetic input is provided:** `data/survey_export.csv` contains 62 made-up records generated by `scripts/generate_sample_data.py`. It covers the documented cleaning cases and 11 deliberately rejected rows. It is a development and demonstration fixture, **not the utility's original supplied export**. If the original becomes available, preserve this fixture under a different name before replacing it, and rerun the verification on the original.
- Use the field definitions and allowed values in the assignment's tables as authoritative: `pole`, `valve`, `manhole`, `transformer`; `active`, `decommissioned`, `proposed`. The story's examples of other asset kinds are context.
- Use one shared validation and cleaning layer for CSV and API writes. Treat duplicate `asset_id` entries in one import as rejects; allow a later valid survey of an existing asset to add a visit without creating a second asset. Document the chosen update behavior and test it.
- Use Docker Compose as the primary development and demonstration workflow. Run PostgreSQL in a `db` service with its data directory on **tmpfs** (no host bind mount, named volume, or anonymous data volume), and the FastAPI application in an `app` service built from a Dockerfile. `docker compose up --build -d` must be the only setup command: after `db` is healthy, the app entrypoint automatically applies Alembic migrations and seeds the new database from the bundled synthetic CSV through the same ingestion pipeline as the CLI. Seed 51 valid assets, write the 11 original-value rejects plus map and summary outputs to a project-mounted output directory, and then start the API. Use a database seed-run marker so restarting only `app` neither imports the CSV again nor creates duplicate visits; an empty `db` after `docker compose down` seeds again on the next `up`. Bootstrap a review administrator automatically with random credentials saved only in a git-ignored, container-local file that the reviewer can read with a documented `docker compose exec` command; never print the password in responses or logs. Database records survive an **application** restart while `db` remains up, satisfying the assignment's restart requirement. `docker compose down` clears them; a **database container** restart also starts empty, so use a full `down`/`up` cycle to reinitialize the review stack. Keep the separate one-command CLI for later daily CSV imports. Expose only the API port by default. For the isolated review stack, keep PostgreSQL passwordless on the private Compose network; production uses environment-supplied database credentials. Generate the API signing secret at runtime and never commit it. README must document `up`, status, credential retrieval, manual CLI use, tests and `down`; no migration or seed command is required from the reviewer. Files the assignment requires as deliverables (CSV, rejects, GeoJSON, text report) remain in the project folder outside the temporary database.
- **Host prerequisite:** `docker` is not currently available on this machine's command path. Install/start Docker Desktop with Compose before the Day 1 container smoke test; the code and Compose files can still be prepared first.
- Suggested stack: Python package with `pyproject.toml`, FastAPI (interactive OpenAPI docs), SQLAlchemy with a configurable `DATABASE_URL` (PostgreSQL in Compose; other databases through configuration), Alembic migrations, a CLI entry point, Pytest, and pinned dependencies. Environment variables configure all secrets and deployment-specific settings. These are implementation choices, not extra requirements from the PDF.
- Use a separate throwaway PostgreSQL test database/container for integration tests; never run tests against the review database. Test the Compose startup, migration, CLI, and HTTP service together before delivery.
- Run tests after each commit. Keep generated outputs and sample data in the repository as required, while keeping real secrets, runtime databases, and local environment files out of Git.

## Day 1 — 16 September: ingest a CSV into a reliable database

**One milestone:** One CLI command accepts the supplied CSV, stores trustworthy records and visits, and preserves every rejected row with reasons. A strict run rolls back completely when any row is rejected.

1. **Commit 1 — sample data, Docker project and schema.** Commit the synthetic 62-row CSV and its generator, installable package, pinned dependencies, `.env.example`, `.gitignore`, Dockerfile and `compose.yaml` with PostgreSQL health check and tmpfs data directory. Add database settings, an Alembic migration for `assets`, `visits` and a seed-run marker, uniqueness and cascading delete constraints, and a throwaway test database fixture. Suggested message: `chore: add sample survey and Dockerized database scaffold`.
2. **Commit 2 — shared cleaning and validation.** Normalize descriptions and surveyor names, case-fold asset types, parse N/S/E/W coordinates, optional elevation, dates and JSON attributes; enforce every rule in section 4.1, including the decommissioned condition rule. Return field-specific validation errors. Test valid boundaries and every listed fault. Suggested message: `feat: normalize and validate survey records`.
3. **Commit 3 — CLI ingestion, outputs and automatic startup.** Add one-command CLI with help, CSV path, optional rejects/map/report paths and `--strict`; check required columns before writing. Process rows independently in normal mode, emit original-value rejects with reasons, print counts, append a dated run log, generate GeoJSON points and the aligned text report. Add asset-type counts, averages, worst asset, extent, repair list, condition bands, nearest-asset haversine calculation, and surveyors by day in reusable reporting functions. Wire the app entrypoint to migrate and seed a new database automatically, recording seed completion only after the import succeeds; bootstrap the review administrator and start the API afterward. Add CLI tests for a bad row, strict rollback, duplicates and output files, plus startup/restart checks for seed idempotency. Suggested message: `feat: ingest CSV and auto-seed review database`.

**Day 1 done when:** `docker compose up --build -d` automatically migrates and seeds a healthy PostgreSQL database and starts the API with 51 assets, 11 documented rejects, and readable GeoJSON/text outputs; the ingest itself finishes in under 5 seconds; restarting only `app` keeps 51 assets without duplicate visits; `docker compose down` followed by `docker compose up` creates a fresh database and auto-seeds it again; and strict mode leaves the database unchanged after a reject. The 51/11 counts are expected for this generated fixture only.

## Day 2 — 17 September: expose and protect the data over the network

**One milestone:** An authenticated API supports all six asset operations, filtering and history, with documented responses and correct roles.

1. **Commit 4 — API foundation and identity.** Add the FastAPI app, `/health` as the sole unauthenticated address, user model and administrator-controlled account creation, password hashing, expiring signed credentials, environment-based signing secret and lifetime, and role checks. Ensure passwords and secrets never enter responses or logs. Add login and permission tests. Suggested message: `feat: add authentication and role-based access`.
2. **Commit 5 — asset operations.** Add list, fetch, create, full replace, partial correction and delete routes. Reuse Day 1 validation, preserve visit history and cascade on delete. Return distinct, consistent responses for creation, deletion, missing record, invalid contents, unauthenticated request and forbidden request. Add endpoint tests against a throwaway database. Suggested message: `feat: implement validated asset CRUD and visits`.
3. **Commit 6 — discovery and data access.** Add filters for type, status, surveyor and score range; case-insensitive name search; offset/limit pagination (default 25, maximum 100) with total count; single-asset visit history and most-visited report. Add the network CSV upload for administrators, reusing the same ingestion pipeline. Verify `/docs` describes inputs and responses. Suggested message: `feat: add search, paging, history and bulk upload`.

**Day 2 done when:** `docker compose up --build -d` serves the API and `/docs`, automated tests cover all six operations, missing records, login, surveyor delete refusal, filter and paging behavior, and bulk-upload counts; manual checks in `/docs` show a login followed by an authenticated request. An unauthenticated asset request differs from a signed-in forbidden delete.

## Day 3 — 18 September: reporting, operational limits, verification and handoff

**One milestone:** The full assignment is reproducible from a fresh checkout, meets its operational requirements, and has the required outputs and recording.

1. **Commit 7 — network reports and cache.** Expose machine-readable summary and repair reports, nearest-asset query and surveyors-by-day query. Cache the summary for at most 60 seconds and invalidate it immediately on every asset add, correction, replacement or removal, including bulk ingestion. Test cache reuse and invalidation. Suggested message: `feat: publish reports with invalidated summary cache`.
2. **Commit 8 — operational safeguards.** Configure exact permitted CORS origins, request limit of 60 per caller per minute with retry information and health exemption, request/response/duration logging and response timing header. Use environment variables for database URL, secret, credential lifetime, origins and request limit. Measure the required timing targets: page of 25 under 500 ms, asset fetch under 200 ms, cached summary under 100 ms, and 62-row ingestion under 5 seconds. Fix measurable failures and add focused tests for limits and configuration. Suggested message: `feat: add rate limits, observability and deployment settings`.
3. **Commit 9 — final verification and deliverables.** Run the full test suite on a throwaway PostgreSQL database and the synthetic CSV end to end through Docker Compose. Commit one rejects CSV, one GeoJSON map file and one text summary report, clearly labeled as generated from synthetic data. Complete README Docker setup, automatic migration/seed behavior, optional later CLI imports, tests, API route descriptions and deployment notes; check a fresh clone needs only `docker compose up --build -d` before review. Record a 5–8 minute demo using Compose, showing automatic startup, rejected rows continuing, `/docs`, login and successful request, denied surveyor delete, cached summary refresh after a change, and rate-limit refusal. Suggested message: `docs: add one-command Docker workflow and demo`.

**Day 3 done when:** a fresh checkout runs through Docker Compose, the tests pass against an isolated PostgreSQL database, `docker compose down` clears the review database, the checked-in example configuration contains no real secrets, the generated files and recording exist, the measured targets are recorded with the machine and synthetic dataset used, and `git log` shows at least three focused commits per day, nine total for this plan. If a performance target cannot be reached, document the measured result and cause rather than claiming it passed. The original utility CSV is still needed to claim verification against the actual supplied data.
